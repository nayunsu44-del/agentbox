# 검증 필요 항목 (run-4)

소스로는 성립하지만 이 환경에서 결정적 증거를 만들지 못한 항목이다. 검증 계획은 레코드의 `validation_plan`을 그대로 옮겼다.

## N1. same_origin compares only the Origin netloc with Host, so an http:// page on the same host passes the CSRF origin check of a TLS deployment and can clear the session cookie

- 지문: `agentbox/api.py:same_origin:scheme-blind-origin-netloc-compare`
- 관련 경로: `agentbox/api.py`, `agentbox/web.py`

**설명.** Every cookie-authenticated UI mutation funnels through api.same_origin (api.py:131-133), which returns True when Origin is absent or when urlsplit(Origin).netloc equals the Host header; the scheme is never compared. A plaintext http://H page is a different web origin from the TLS deployment https://H but carries the same netloc, so the gate accepts it. Independently reproduced (agents/v02/scratch/v02_origin.py, artifact v02_origin.out; api.build with docker.from_env stubbed, ASGI served as https://agentbox.example): Origin http://agentbox.example was accepted for POST /login (303, issuing the Secure SameSite=strict HttpOnly host-only session cookie), POST /ui/approvals/apr_000000000000/approve (200; box.decide entered with the '*' session and rendered approval-not-found), POST /ui/sandboxes (handler reached box.create_sandbox) and POST /logout (303; end_ui_session entered, server session ended - a later GET /ui with the same cookie redirected to /login). Origin https://agentbox.example was accepted identically; Origin https://evil.example, Origin: null, Origin http://agentbox.example@evil.example and Origin http://agentbox.example:8443 against Host agentbox.example were all 403; a POST with no Origin was accepted. Consequence (1): where a browser attaches the Strict cookie to a cross-scheme POST, the human-scoped action runs - approve/deny for a known apr_ id, a sandbox built for an attacker-chosen source_dir, or server-side session end. Consequence (2), browser-independent once the request is sent: POST /logout answers even a cookieless cross-origin request with 303 plus an unconditional cookie-clearing Set-Cookie (web.py:149-150), so a page served at http://H forces a client-side logout while the server-side session survives. No anti-CSRF token, Referer or Sec-Fetch check exists anywhere in agentbox/ (grep finds none) and the only response-wide guard is X-Object-Frame/CSP frame-ancestors (api.py:66), which stops iframe clickjacking but not a top-level auto-submitted form; no Strict-Transport-Security is emitted in agentbox/ or deploy/ (no response carries one; only audit docs mention it), so nothing forces the upgrade of http://H. The decisive unknown stays the browser's schemeful same-site behaviour: the run-3 loopback Chromium 141 run had the Secure cookie withheld (only the forced browser logout occurred), no browser exists in sbx, and Firefox/WebKit are unobserved, so whether consequence (1) is reachable cannot be decided from source or from this sandbox.

**막힌 지점.**
- Browser behaviour (decisive): whether a browser an operator actually uses attaches the Secure SameSite=strict session cookie to a cross-scheme http://H -> https://H form POST. Chromium 141 withheld it (docs/security-audit/run-3/agents/parent-live/artifacts/l3/l4.out:4, reported, not re-run in run-4); Firefox and WebKit current behaviour and the legacy cut-offs are untested, no browser exists in sbx, and the answer cannot be derived from source. Without the cookie only consequence (2), the client-side forced logout, remains.
- Network position: whether an attacker can serve plaintext http://H on the deployment host name at all (on-path network attacker, a plaintext listener on port 80, or a DNS/HTTP hijack). No Strict-Transport-Security is emitted anywhere in agentbox/ or deploy/, so nothing forces the upgrade, but whether an on-path attacker and browser preload state are in scope is an owner decision.
- Deployment shape: whether both schemes are exposed at the same effective netloc (direct TLS on 443 plus cleartext 80, or behind-proxy mode where Caddy owns the http->https redirect). In a loopback http-only deployment the scheme fork does not exist, and if HSTS or a preload entry is present the http page never loads.

**로컬 검증 계획.** Repo-side half is done and reproduced by the verifier: agents/v02/scratch/v02_origin.py builds the real app (api.build with docker.from_env stubbed) and drives it over ASGI as https://agentbox.example - cross-scheme Origin accepted on /login, /ui/approvals approve, /ui/sandboxes and /logout, foreign/null/userinfo/port-mismatch 403, /logout always emitting the clearing Set-Cookie; artifact v02_origin.out. Remaining decisive step is a loopback browser lab run outside sbx (parent-live): map H to 127.0.0.1, start agentbox with --tls-cert/--tls-key (self-signed, lab-trusted) on https://H:443 with a dummy human token, and a plaintext http://H:80 page that auto-submits a top-level form to https://H/logout and to https://H/ui/sandboxes with source_dir set; log in on https://H, open http://H, and record (a) whether agentbox_session is sent on the POST, (b) whether the response is 303/200 (accepted) rather than 403, (c) for /logout whether the server session ends (GET /ui then 303 /login) and whether a ui_logout row appears in /audit, (d) for /ui/sandboxes whether a new sandbox exists. Repeat on current Firefox and WebKit and on any engine or policy that disables schemeful same-site. Regression: change same_origin to compare BOTH the scheme and the netloc, taking the served scheme from request.url.scheme (already used at api.py:136 and web.py:114, and X-Forwarded-Proto-aware under cli.py:126) instead of the headers-only signature at api.py:131; then both cross-scheme POSTs must return 403 and the clearing Set-Cookie must disappear, while Origin https://H with Host H still passes and the existing tests/test_unit.py suite stays green.

**배포 검증 계획.** Owner confirms, without probing live endpoints: (1) whether the operator-facing host name sends Strict-Transport-Security or is on the browser preload list; (2) whether a plaintext http:// listener for that name is reachable (direct TLS on 443 plus cleartext 80, or a TLS proxy fronting the plaintext port where the http->https redirect is the only barrier) and whether an on-path attacker is in scope; (3) which browser engines and versions operators use; (4) whether any operator browser or policy lacks schemeful same-site. If HSTS is present and every browser is schemeful, only the browser-independent forced-logout residual from the unconditional delete_cookie at web.py:149-150 remains, and the same scheme comparison removes it.

## N2. Agent-grown audit and approval rows in the shared control-plane SQLite file have no aggregate bound or retention, so an agent can fill the host disk and neither recovery path keeps the audit chain

- 지문: `agentbox/audit.py:append:agent-grown-rows-in-shared-sqlite-have-no-aggregate-bound-or-retention`
- 관련 경로: `agentbox/api.py`, `agentbox/audit.py`, `agentbox/service.py`

**설명.** Every accepted agent tool request appends two audit rows (tool_request before the policy decision, policy_decision as soon as decide() returns) before any approval request, snapshot or execution, a risky call adds an approval_requested row plus an approvals row holding the full raw args, and every failed POST /approvals/{aid} adds an approval_forbidden row. Args are now capped per record (80,000-byte command is stored as a 16,384-byte head), but nothing bounds the tables: in an isolated fixture two rows per call added 17,203 bytes to the .db file, identically at n=20 and n=40, and 512 bytes per call for {command: ls}; five approval rows of 400,000-byte args took 2,007,040 bytes and every row survived executed/denied/expired. Triggers abort UPDATE and DELETE on audit, grep finds no DELETE for audit or approvals, no VACUUM, no count/size quota and no retention job, so growth is permanent and host disk is the only limit. When the volume fills, AuditLog.append raises AuditWriteError, which service.py turns into 503 for tool calls, human lifecycle, approval decisions and handbacks, so all sandboxes stop rather than the offending one. Recovery is not available either: deleting the oldest rows made verify() fail permanently at the first survivor (broken_at=7, 'id가 1 다음에 7로 건너뜀'), while deleting every row made verify() report ok=True with checked=0, so an operator must choose between permanently broken verification and a silently erased history.

**막힌 지점.**
- Free space, any filesystem or volume quota, and the planned lifetime of the volume holding data/agentbox.db (config.py:29 home=./data, config.py:84-86 db_path, deployed as a host bind mount at deploy/docker-compose.yml:26-28) are deployment facts. Nothing in the repository bounds stored total: no retention, no count or size quota, no VACUUM. At the measured 17,203 bytes per maximum-size tool call (512 bytes for a trivial call) the time to exhaustion depends entirely on that free space, from minutes on a small volume to months on a large one, and no repository fact decides it.
- The call rate an agent can sustain is partly a deployment fact: the repository has no rate limit on the tool route, tool_concurrency=4 (config.py:53) and the 32-thread tool_pool (api.py:103) bound concurrency only, and the shipped Caddyfile is a bare reverse_proxy (deploy/Caddyfile:4-6), but any operator-added proxy or network control is outside the source.
- Whether operators prune or rotate that SQLite file out of band, and which loss they accept, is a deployment/owner decision: source and fixture show that partial pruning permanently fails /audit/verify (audit.py:230-236) while total truncation passes as an empty log, so the product offers no capacity recovery that keeps the history verifiable.

**로컬 검증 계획.** Already performed in the approved sandbox (tools/sbx.py v03: /target read-only on PYTHONPATH, /scratch writable, no network, no Docker socket, uid 65534, 512 MiB, 120 s). Built AuditLog and ApprovalStore on scratch databases and replayed exactly what _call_tool writes: (1) _logged_args('exec', {'command': 'a'*80000}) returned args_head of 16,384 bytes and args_bytes 80,015; (2) 20 and 40 pairs of tool_request plus policy_decision rows added 344,064 and 688,128 bytes after PRAGMA wal_checkpoint(TRUNCATE), i.e. 17,203 bytes per call at both sizes, and 40 pairs with {'command': 'ls'} added 20,480 bytes, i.e. 512 bytes per call; (3) DELETE FROM audit and UPDATE audit both failed with sqlite3.IntegrityError 'audit log is append-only'; (4) dropping only the delete trigger and removing ids 1..6 left verify() returning ok=False, checked=0, broken_at=7, reason 'id가 1 다음에 7로 건너뜀', while deleting every row left verify() returning ok=True with checked=0; (5) five ApprovalStore rows of 400,000-byte args took 2,007,040 bytes (401,408 each) and all five were still listed after executed, denied and expired, with no delete method on the store; (6) approvals.list() re-parses full args. The disk-full to AuditWriteError to 503 conversion was not exercised (filling a filesystem is a saturation test); it rests on audit.py:193-194 wrapping sqlite3.Error and the fail-closed handlers cited in the trace. Output: scratch/fixout.txt and scratch/fixout2.txt; the numbers above were observed directly, the files are supplementary.

**배포 검증 계획.** Owner-observed on a throwaway deployment, never a shared or production host, and without filling the volume: record the free space and any quota on the volume holding data/agentbox.db; issue 200 bounded tool calls from one agent token with 80,000-byte exec commands (denied calls are sufficient, since the two audit rows are written before any execution) and 200 with {command: ls}; confirm the .db size delta is about 3.4 MB and 0.1 MB respectively and that it does not shrink after the calls stop, after sandbox deletion, or after any documented maintenance command; then check whether the operator has any out-of-band retention or rotation for that file, and confirm that once the volume is full the tool route and the human lifecycle route both return 503 from AuditWriteError while other sandboxes are unaffected by definition only. Extrapolate from the per-call delta instead of filling the disk.

## N3. list_dir, outbox_list, preview glob expansion and screenshot buffer unbounded container output in the shared control-plane process

- 지문: `agentbox/sandbox.py:container-output-readers-without-_Head-byte-cap`
- 관련 경로: `agentbox/api.py`, `agentbox/sandbox.py`, `agentbox/sandbox_desktop.py`, `agentbox/service.py`

**설명.** On a sandbox that the agent token controls, four control-plane readers take the whole container-produced stream through Docker's non-streaming exec_run, with no byte cap and, for three of them, no container-side timeout: SandboxManager.list_dir (sandbox.py:428) runs `ls -la` on any /workspace or /source path; SandboxManager.outbox_list (sandbox.py:534) runs an unbounded `find -maxdepth 1 -printf`; SandboxManager._expand (sandbox.py:560) globs a preview pattern; DesktopTools.screenshot (sandbox_desktop.py:86-88) `cat`s /home/desktop/.cache/agentbox-shot.png and only then checks the PNG magic. _truncate (sandbox_common.py:24-32) and _parse_outbox (sandbox.py:111-124) run after the whole buffer exists, so they bound the returned value, not the peak. The peak is paid by the one shared FastAPI process, so one sandbox's listing is charged to every sandbox. Measured locally against the real reader functions with a fake exec_run: a 16 MiB stream makes list_dir peak at 16.19 MiB, against 0.32 MiB for exec's _Head reader on the same stream; 5.0 MB of find output becomes 58.6 MiB retained and 72.6 MiB peak after _parse_outbox (12.3x, record count uncapped); 4.2 MB of glob output becomes 209,715 Python strings; an 8 MiB PNG is accepted unchanged and then base64-encoded to 11.2 MB for the agent response (service.py:143). The screenshot path is the one with superlinear amplitude: the shot file sits in the desktop user's writable home (_SHOT, sandbox_desktop.py:32), so uid 1001 can point it at a character device and turn one cheap call into up to 15 s of unthrottled `cat`, bounded only by a wall clock (_X_TIMEOUT, sandbox_desktop.py:26,46-50), whose exit-code check also runs after the read. The host-disk half of the claim is narrower than proposed: service.py:328 writes the captured PNG with no size check, but only after the magic test passes, so a /dev/zero symlink costs memory and no disk; a huge PNG-prefixed file is needed for the disk variant. The list_dir/outbox_list/_expand variants are ~1:1 with container output, and the container's output ceiling is its writable layer, which the repository caps only when the optional AGENTBOX_DISK is set (config.py:42, sandbox.py:263-264).

**막힌 지점.**
- The decisive quantity - how much memory the control plane actually holds while a real container streams - is produced inside the docker SDK's non-streaming exec_start reader. The approved sandbox has no Docker daemon or socket (uid 65534, no /var/run/docker.sock), so no real exec stream can be created or sized; the peaks reported here come from an in-process fake exec_run that hands the real reader functions pre-built bytes, which understates the real peak because the SDK buffers the same bytes as well.
- The superlinear variant needs /home/desktop/.cache/agentbox-shot.png replaced by a symlink to /dev/zero (or to a huge PNG-prefixed file) by uid 1001 inside a live agentbox-desktop sandbox; the audit sandbox has neither that image nor an X session, and the control plane's own `scrot -o -z` overwrites the path on the non-symlink case.
- Whether the resulting peak is fatal depends on owner-side topology that the repository does not fix: deploy/ sets no memory limit for the agentbox service, the host's memory and any cgroup limit are unknown, AGENTBOX_DISK is unset by default, and the blast radius (control-plane restart drops every sandbox's desktop session and in-flight approvals) is an operational fact.

**로컬 검증 계획.** Owner-run on a disposable Docker-backed sandbox with AGENTBOX_DISK=2g and no network. (1) Create ~200k empty files in /workspace using unapproved batch `touch` calls (touch is in the read-only allowlist, default_policy.yaml:25-27) or one gated exec. (2) Record VmHWM from /proc/<pid>/status of the control-plane process, call POST /sandboxes/{sid}/tools/list_dir {"path":"/workspace"} with a dummy agent token, record VmHWM again, and confirm the returned listing stops at 64 KiB while the peak grew by roughly the raw ls size. (3) Control: run the same directory through the capped exec reader (`ls -la /workspace`) and confirm the delta stays near 64 KiB. (4) Put 200k files in /workspace/outbox, call GET /sandboxes/{sid}/outbox, and check for the ~12x parse amplification measured here. (5) Send one `rm /workspace/*` exec so the REQUIRE_APPROVAL branch runs _preview before any human decision, and measure the _expand cost. (6) Desktop variant: in a disposable desktop sandbox, as uid 1001 point the shot path at /dev/zero, call POST /tools/screenshot, and stop the test as soon as VmHWM growth is visible, noting whether the 15 s timeout keeps it under the host limit.

**배포 검증 계획.** Owner-observed on the compose stack: watch the agentbox container's RSS while a dummy agent lists a 200k-entry /workspace, compare it with the same agent running an allowlisted `ls -la` through the capped exec reader, and record whether the service has a cgroup memory limit and what an OOM does to running sandboxes and pending approvals. Then, with captures enabled, watch the same RSS during a burst of gated calls against a desktop sandbox whose shot path was replaced by a device symlink, and confirm that no file appears under settings.home/captures in the /dev/zero case while a huge PNG-prefixed file does produce one.

## N4. GUI burst stray kill spares a uid-1001 process in a burst-start session whose pid the client-declared _NET_WM_PID window list names

- 지문: `agentbox/sandbox.py:gui_strays:client-declared-net-wm-pid-exempts-baseline-session-process`
- 관련 경로: `agentbox/api.py`, `agentbox/gui_bursts.py`, `agentbox/gui_state.py`, `agentbox/sandbox_desktop.py`, `agentbox/service.py`

**설명.** Verified in the audited tree (9805d91): at GUI-burst close GuiBursts._finish (gui_bursts.py:120) calls _stop_strays, which reads desktop_processes (gui_bursts.py:83) and kills gui_strays(procs, wins, burst['pids']) (gui_bursts.py:84-85). For a new uid-1001 process the only remaining exemption is the window test: p['pid'] in window_pids or a non-baseline ancestor pid in window_pids (gui_state.py:85-86); baseline pids, pid 1, other uids and docker-exec roots are exempted earlier (gui_state.py:80). window_pids are the decimal tokens of `xdotool getwindowpid` over `xdotool search --onlyvisible --name .` (sandbox_desktop.py:59-61), i.e. the _NET_WM_PID property the X client writes for itself; the parser filters with isdigit only, never checks that the pid owns a window or is the declaring client, and xdotool is run as the desktop account on the desktop-owned display (sandbox_desktop.py:46-47, images/desktop/agentbox-desktop-start:20,30,38). I re-ran the real gui_state.gui_strays and the real GuiBursts._stop_strays in the sandbox (agents/v05/artifacts/v05_probe.out): a headless uid-1001 daemon 300 in the burst-start session sid 1, parented by the baseline Thunar 85, is killed when window_pids is empty (line 2) and is spared when the window list merely names 300 (line 3); naming an unrelated pid 301 does not spare it (line 4), and a windowed but baseline ancestor 85 does not spare it (line 5). With the real _stop_strays the forged case killed nothing and emitted no gui_processes_stopped record at all, while the control case killed [300] and logged it (lines 20-22). Two preconditions bound the claim, and both are runtime facts of the image rather than source facts. (1) The window test is reached only when p['sid'] is in base_sids, the sessions of the uid-1001 baseline pids (gui_state.py:63,82-84); a new session is killed regardless of window, which my run confirms for a daemon in sid 777 (line 8). tests/test_unit.py:330-334 encodes exactly that for a terminal opened during a burst: the terminal window 150 is spared but its shell 152 and the shell's job 160 are killed as a new session, so a daemon typed into a terminal opened during the burst is not in this candidate's class. (2) The attacker needs an X client that can set _NET_WM_PID to another process's pid and then have xdotool report it; the image recipe installs xdotool, socat and x11-xserver-utils but not x11-utils (xprop), python or a compiler (images/desktop/Dockerfile:17-23), so whether such a client exists in the running image is unobserved. Impact is bounded and detective-control shaped: GUI input is approval-free by design (N-1) and the burst's snapshot and gui_changes are its documented record. A spared daemon keeps writing /workspace after the close, where the only manifest read (gui_bursts.py:122) has already happened, and its writes produce no gui_changes and no gui_processes_stopped row; because it is then present at the next burst open (gui_bursts.py:70,76), gui_state.py:80 treats it as baseline forever, which is the candidate's 'survives every burst close'. Calibration, not dismissal: the by-design ancestor clause already spares a helper of any windowed app opened during the burst (tests/test_unit.py:335-336; my line 9), so the forgery route adds capability mainly for a process with no new windowed ancestor, for example one started from a baseline windowed app such as the pre-existing file manager (tests/test_unit.py:337 keeps such a script in the kill list).

**막힌 지점.**
- The decisive platform step is not observable here: this sandbox has no X server and no X client. Reproduced in the run (agents/v05/artifacts/v05_probe.out:25-33): DISPLAY unset, /tmp/.X11-unix absent, xdotool/xprop/Xvfb absent, python Xlib absent. So neither 'a uid-1001 client sets _NET_WM_PID to another process's pid' nor 'xdotool getwindowpid reports that value for its window' can be observed.
- Related image fact: the recipe (images/desktop/Dockerfile:17-23) provides xdotool and socat but no xprop/x11-utils, no python and no compiler, and xdotool has no generic property setter. Whether the running image contains any program able to write an arbitrary _NET_WM_PID (base-layer or Xfce component, or a hand-written X11-protocol client over the unix socket via socat) must be read from the live image; if none exists the forgery route is refuted for this image and only the by-design ancestor route remains.
- Reachability needs the daemon's sid to be one that existed at burst open (gui_state.py:63,82-84): a typed command's shell normally gets a new session (tests/test_unit.py:330-334, my line 8). Whether GUI-only input can place a headless daemon in the startxfce4 session is a runtime property of the image's terminal/launcher behaviour.
- Observing survival after a real idle close needs the Docker-backed desktop container (docker exec for ps, xdotool, kill and the audit read); the Docker daemon is forbidden in this verifier sandbox, so the end-to-end kill/no-kill result and the missing gui_processes_stopped row are shown only against the real pure function and the real _stop_strays with a fake container.

**로컬 검증 계획.** Disposable agentbox-desktop:0.1 container, network none, built from the audited tree, dummy files only. (1) Record `command -v xprop python3 gcc cc socat xdotool` and `dpkg -l x11-utils` as the property-setter inventory. (2) Start the desktop; as the desktop account via docker exec -u desktop, first start the helper in a burst-start session (launched from the panel/Thunar or from a pre-existing windowed app) and confirm with `ps -eo pid=,ppid=,sid=,uid=,args=` that its sid equals a session that predates the burst; then start the headless writer `sh -c 'while :; do date +%s >> /workspace/_v05_probe; sleep 2; done' &` in that same session. Expected if the finding holds: the writer pid is absent from the list, while the same call with wins=set() returns it. (5) Call kill_processes(sid, returned list), then confirm by ps that the writer still runs and that /workspace/_v05_probe's mtime advances past AGENTBOX_GUI_SNAPSHOT_IDLE. Non-destructive: dummy probe file only, writer killed and container discarded at the end.

**배포 검증 계획.** Owner-observed on a disposable desktop sandbox with dummy tokens and dummy files: during a real burst drive the agent's click/type to open a terminal from the panel and start `nohup sh -c "while :; do date +%s >> /workspace/_v05_probe; sleep 2; done" &`, plus the property helper if the image has one. ## N5. The shared control-character filter misses U+061C - the only Unicode Bidi_Control code point it omits - plus the Cf/Zl/Zp invisibles, and the approval card renders them raw beside the argv that will execute

- 지문: `agentbox/templates/_approvals.html:exec-command-bidi-controls-unneutralized`
- 관련 경로: `agentbox/api.py`, `agentbox/service.py`, `agentbox/templates/_approvals.html`, `agentbox/web.py`

**설명.** Source and a local render confirm a residual gap in the run-3 fix, but not its security outcome. web._shown (web.py:33-37) sends every template output through display.escape_controls with keep_newlines=True (web.py:94), and that class does neutralise the run-3 payloads: rendering the real _approvals.html through web.py's exact Jinja wiring turns U+200E/U+200F/U+202A-E/U+2066-9 into literal \uXXXX escapes while markupsafe escapes markup. The class is hand-written (display.py:13,15) and covers 11 of the 12 Unicode Bidi_Control characters: U+061C ARABIC LETTER MARK is absent, and so are U+200B-200D, U+2060, U+FEFF, U+00AD, U+2028 and U+2029. Measured in the approved sandbox, all of them survive raw in both the command <pre> and the affected-path cell of the same card, and cli._safe (cli.py:33-35) is byte-identical, so the terminal approval view carries the same gap rather than disagreeing with the web view. What is not established is whether any of them lets the card read as a different command in the operator's browser. U+061C is bidi class AL, a strong right-to-left character, not an isolate: on its own it cannot reverse a run of ASCII letters (they stay strong L), and its bidi effect is limited to the resolved direction of adjacent neutral punctuation sitting between two of them. U+2028/U+2029 are mandatory line breaks that would split one argv into two visual lines inside the same pre block without hiding either line, and the remaining characters are invisible rather than reordering. That leaves a display-integrity question whose answer lives in the renderer, which no surface in this audit can observe.

**막힌 지점.**
- No browser or terminal renderer is reachable from the approved sandbox (python3 plus the repo and jinja2/fastapi only, no network, no display), so the rendered order of the residual code points cannot be observed. The local run proves the reachability half only: U+061C, U+200B-200D, U+2060, U+FEFF, U+00AD, U+2028 and U+2029 arrive raw in the card's <pre> and path cell while the argv executed by service.decide (service.py:398,421 -> service.py:126) keeps the same code points.
- The decisive fact is whether a residual code point makes the card read as a different command. U+061C is bidi class AL, a strong right-to-left character that cannot reverse ASCII letter runs; U+2028/U+2029 add a mandatory break inside the same pre block but hide nothing; U+200B-200D/U+2060/U+FEFF/U+00AD are invisible and only affect how individual characters join.
