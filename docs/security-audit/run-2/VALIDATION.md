# agentbox — run-2: needs_validation 5건 실측 검증

run-1에서 소스만으로는 결론을 못 낸 5건(N-1~N-5)을 실제 Docker 위에서 돌려 확인했다. **5건 모두 확정**됐고, N-2를 검증하다 **새 문제 1건**(사람 API 스레드 굶주림)을 찾았다. 5건은 수정했고, N-1은 사용자가 고른 방안 C·A·G로 부분 완화했다.

- 검증일: 2026-10-22
- 환경: Docker 29.9.1 (runc, overlayfs/containerd 스냅샷터, userns 리매핑 없음, cgroup v1), 4 vCPU / 메모리 15GB. 이미지 `buildpack-deps:noble-curl`, `agentbox-desktop:0.1`(`images/desktop`에서 빌드).
- 원칙: 모든 재현은 이 세션의 일회용 Docker 안에서 에이전트 토큰(또는 해당하면 사람 토큰)으로 HTTP API만 써서 했다. 공유·운영 시스템은 건드리지 않았다.
- 구조화 레코드: [`findings.json`](findings.json) (run-1의 9건 + 신규 1건 = 10건, 확정 9 · 기각 1, `validate-findings.cjs` 통과). run-1 디렉터리는 1차 감사 기록으로 그대로 둔다.
- 재현 스크립트: [`repro/`](repro). 레포 루트에서 `python3 docs/security-audit/run-2/repro/<이름>.py` (Docker 데몬, `pip install -e '.[test]'` 필요. `n5_spoof.py`는 `pyte` 필요).

## N-1 GUI 도구 → 터미널 → 승인·스냅샷 없는 명령 실행 (High, 부분 완화)

**재현** (`repro/n1_gui.py`): 데스크톱 샌드박스에서 에이전트 토큰으로 GUI 도구 세 번만 호출했다.

1. `key ctrl+alt+t`: Xfce 기본 단축키로 `xfce4-terminal`이 열린다. 하단 독에도 터미널 아이콘이 있어 `click` 한 번으로도 된다.
2. `type "id > /workspace/outbox/gui-id.txt; rm -f /workspace/victim.txt"`
3. `key Return`

**관측**:
- 세 호출 모두 200을 받았다. 화면에 `Terminal - desktop@…`이 떴다([스크린샷](n1-terminal-via-gui-tools.png)).
- `victim.txt`가 삭제됐다.
- `gui-id.txt`에 `uid=1001(desktop) … groups=1001(desktop),1000(agent)`가 기록됐다.
- 승인 0건, 스냅샷 0건이다. 감사 로그에는 `tool_request/type`으로 입력 문자열이 남지만, 정책 검사와 스냅샷은 적용되지 않았다.

**처음에 바로 고치지 않은 이유**: 데스크톱은 원래 프로그램을 실행할 수 있는 환경이다. 터미널을 지워도 다른 길이 남는다: Applications 메뉴의 "Run Program", Thunar에서 실행 권한을 주고 실행하기, autostart 항목 등. 그래서 다음 중 무엇을 고르는지가 제품 결정이다.

1. **문서화**: "데스크톱 템플릿의 GUI 도구는 컨테이너 안 uid 1001 임의 실행과 같다. exec 허용 목록·승인·AP-2는 GUI 경로를 막지 않는다"를 README에 명시한다. 모든 선택지에 공통이다.
2. **GUI 입력 전 자동 스냅샷**: 권장. AP-2의 복구 가능성을 GUI 경로에도 되살린다. `AGENTBOX_SNAPSHOT_QUOTA`와 맞물린다. 승인 우회는 남는다.
3. **GUI 입력을 기본 승인 대상으로**: 보장은 가장 강하지만 조작마다 승인이 필요해 템플릿을 사실상 쓰기 어렵다.

터미널 제거 같은 하드닝은 경계가 되지 못하고, 화면을 인수한 사람의 사용성만 떨어뜨려 권장에서 뺐다.

전체 방안 8가지와 비교·권장 조합은 [`N-1-OPTIONS.md`](N-1-OPTIONS.md)에 정리했다.

**조치** (`3028b68`·`d677348`, 사용자가 방안 C·A·G 선택):
- `click`·`type`·`key`는 GUI 구간이 시작될 때(60초 쉬었다 다시 입력, 또는 사람이 화면을 돌려준 뒤 첫 입력)와 구간 중 10분마다 직전에 스냅샷을 뜬다.
- 스냅샷 상한에 닿으면 구간 시작 입력만 승인을 거치고, 승인 경로의 스냅샷이 구간을 새로 열어 그 뒤 입력은 다시 바로 돈다.
- 같은 공격을 다시 돌리면 파일은 여전히 지워지지만, `key` 직전 스냅샷이 생기고 그것으로 복원하면 `victim.txt`가 돌아온다(`repro/n1_gui.py`).
- G: 구간 시작 때 `/workspace` 파일 목록을 root로 잡아 두고, 구간이 끝나면(입력 60초 끊김, 다음 구간, 화면 인수) 추가·변경·삭제 파일을 `gui_changes`로 감사 로그에 남긴다. 시작 스냅샷 id도 같이 남긴다. 같은 공격 뒤 타임라인에 "삭제됨: victim.txt"가 보인다.
- A: README 데스크톱 절에 "GUI 도구는 승인을 거치지 않는 실행 경로" 주의 상자를 넣었다.
- **남는 것**: 승인 우회 자체, 되돌릴 때 그 구간의 정상 작업 손실, GUI로 띄운 백그라운드 프로세스의 구간 밖 변경. README 알려진 한계에 적었다.

## N-4 `source_dir` → 사람 토큰 유출 (High, 수정)

**재현** (`repro/n4_source.py`):
- 운영자가 프로젝트 폴더에서 `serve`(기본 `AGENTBOX_HOME=./data`)하고 `source_dir="."`로 샌드박스를 만든다.
- 에이전트가 `read_file /workspace/data/human_token`으로 사람 토큰을 그대로 읽는다.
- 에이전트의 `rm` 요청이 승인 대기에 걸리면, 에이전트가 그 토큰으로 `POST /approvals/{id}`를 보낸다. **200 executed.**
- `data/sources/<다른 샌드박스>`도 보인다.

**root 동등성**: runc에 userns 리매핑이 없다. 같은 능력 집합(CHOWN, DAC_OVERRIDE, FOWNER, SETUID, SETGID, no-new-privileges)으로, uid 4242 소유 0600 파일(0700 폴더 안)을 `cp -a`와 `chown`으로 옮기자 uid 1000이 내용을 읽었다.

**수정** (`e56e2a9`):
- 사람이 준 `source_dir`가 데이터 폴더나 DB 폴더와 같거나, 그 안이거나, 그것을 포함하면 400으로 거부한다.
- 그 밖의 호스트 경로는 운영자 책임이다. README 알려진 한계에 적었다.

## N-2 exec 출력 메모리 적재 (Medium, 수정)

**재현** (`repro/n2_parallel.py`, 실제 `agentbox serve`): `cat /dev/zero`(허용 목록, 승인 없음)를 기본 60초 제한으로 실행했다.

| 조건 | 서버 RSS 증가 |
|---|---|
| 요청 1개 | +151MB (~3.3MB/s × 60초, 64KB만 남기고 버림) |
| 같은 토큰으로 동시 16개 | +1,153MB (최고 1.2GB) |

증가 폭은 컨트롤 플레인 CPU 처리량 × 제한 시간으로 정해진다. 15GB 호스트는 버텼지만, 작은 VM이나 compose 메모리 제한 아래에서는 단일 컨트롤 플레인 프로세스가 OOM으로 죽는다.

**수정** (`c6a0a3c`):
- `exec_create`와 `exec_start(stream=True, demux=True)`로 받고, 각 스트림의 앞 64KB만 들고 나머지는 길이만 센다(`_Head`).
- 종료 코드는 `exec_inspect`로 읽는다. 결과 형식은 그대로다.
- 수정 후: 요청 1개 +0MB. 동시 16개는 +3MB(4개 실행, 12개는 429).

## 신규: 사람 API 스레드 굶주림 (Medium, 수정)

**재현** (`repro/n2_starve.py`): 출력 없는 허용 명령 `tail -f /dev/null`을 동시에 45개 보낸 뒤 사람의 `GET /approvals` 응답 시간을 쟀다.

| 조건 | 응답 시간 |
|---|---|
| 5개 | 0.1초 |
| 45개 | 18.6초 (제한 20초의 나머지 전부) |

기본 제한 60초에서 이를 반복하면, 사람은 승인·거절·샌드박스 삭제를 계속 못 한다.

**수정** (`c6a0a3c`):
- 도구 호출 엔드포인트를 비동기로 바꾸고, 사람 API와 다른 전용 스레드 풀(32)에서 실행한다.
- 샌드박스별 동시 호출 상한 `AGENTBOX_TOOL_CONCURRENCY`(기본 4)를 두고, 넘으면 429를 준다.
- 수정 후: 기본 설정에서 0.0초, 상한을 끄고 전용 풀만 있어도 0.1초.
- 참고: `TestClient`는 요청마다 이벤트 루프를 따로 만들어 이 문제가 재현되지 않는다. 그래서 회귀 테스트는 실제 서버 프로세스를 띄운다.

## N-3 스냅샷 무제한 누적 (Medium, 수정)

**재현** (`repro/n3_snapshots.py`, `repro/n3_amplify.py`):
- 에이전트 토큰만으로 같은 파일을 200번 덮어썼다. 200번 모두 200, 승인 0건, 스냅샷 이미지 200개. 샌드박스를 지워도 200개가 남았다.
- **증폭**: `docker commit`은 매번 쓰기 레이어 전체를 복사한다. 에이전트가 새 파일(승인·스냅샷 없음)로 `/workspace`를 50MB로 키운 뒤 2바이트 파일을 10번 바꾸자 디스크가 +811MB 늘었다(스냅샷당 약 81MB). 삭제 뒤에도 595MB가 남았다.

**수정** (`4826cb5`):
- `AGENTBOX_SNAPSHOT_QUOTA`(기본 50). 상한에 이르면, 스냅샷이 필요한 허용 호출을 승인(`snapshot-quota`)으로 돌린다. 승인 경로는 실행 직전에 스냅샷을 그대로 뜨므로 AP-2가 유지된다.
- 샌드박스를 지우면 그 스냅샷 이미지도 지운다.
- 오래된 스냅샷을 지우는 방식은 택하지 않았다. 에이전트가 덮어쓴 파일의 복원 지점을 밀어낼 수 있기 때문이다.
- 수정 후: 200회 시도 중 50회 실행, 150회 승인 대기. 이미지 50개, 삭제 후 0개.

## N-5 터미널 승인 화면 스푸핑 (Medium, 수정)

**재현** (`repro/n5_spoof.py`):
- 에이전트가 `python3 -c "import shutil; shutil.rmtree('/workspace')" #\r\x1b[2K    \x1b[36mls -la /workspace`를 요청한다.
- 실제 API에서 받은 승인을 `_show_approval`로 그리고 VT 에뮬레이터(pyte)에 넣었다.
- 운영자 화면의 "실제로 실행될 명령"에는 `ls -la /workspace`만 보였다. 이 명령은 영향 계산이 안 돼 화면이 "명령 원문을 확인할 것"이라고 안내하는데, 그 원문이 위조된 것이다.
- 감사 타임라인(`stderr_head`)도 같은 문제였다. 웹 승인 화면은 안전하다(Jinja autoescape).

**수정** (`1a9bb0f`):
- `cli._safe`가 C0·DEL·C1 제어 문자와 양방향 재배치 문자를 `\x1b`, `‮`처럼 보이게 바꾼다.
- 승인 화면, 승인 후 출력, 감사 타임라인에 적용했다.
- 여러 줄 명령은 줄마다 찍고 줄 수를 보여, 빈 줄로 진짜 명령을 화면 밖으로 밀어내지 못하게 했다.

## 검증 중 본 다른 것 (수정 범위 밖)

- README 알려진 한계에 이미 적힌 문제가 있다: FIFO를 `read_file`로 읽으면 그 호출이 멈춘다. 이제 도구 호출은 전용 풀과 샌드박스별 상한 안에서 돌아서 사람 API에는 영향이 없다. 하지만 해당 샌드박스의 도구 슬롯은 묶일 수 있다.
- 요청이 몰리면 승인 대기 카드가 그만큼 쌓인다(N-3 수정 후 상한 초과분, 기존 `rm` 요청 등). 승인 큐에 대한 상한·묶음 처리는 없다.
