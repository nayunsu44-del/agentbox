# N-1 대응 방안 정리: GUI 도구로 승인·스냅샷 없이 명령 실행

검증 결과는 [`VALIDATION.md`](VALIDATION.md)의 N-1 절에 있다. 이 문서는 고치는 방법을 빠짐없이 늘어놓고 비교한다. **결정: 방안 C(GUI 구간 스냅샷)를 골라 `3028b68`에서 적용했다. 맨 아래 "결정과 남은 것" 참고.**

## 먼저 문제를 정확히

데스크톱 샌드박스에서 에이전트의 GUI 도구(`click`·`type`·`key`)는 화면 계정(uid 1001)으로 키보드·마우스를 움직인다. 이 계정은 `agent` 그룹이라 `/workspace`를 쓸 수 있다. 실측에서는 `Ctrl+Alt+T` → 명령 입력 → `Return`으로 터미널을 열어, 파일을 승인 0건·스냅샷 0건으로 지웠다.

중요한 점이 하나 있다. **터미널은 문제의 일부일 뿐이다.** 데스크톱의 원래 목적이 GUI 앱으로 `/workspace` 파일을 다루는 것이다. 그래서 터미널이 없어도 다음은 원래 된다:
- 파일 관리자(Thunar)에서 파일을 지우는 것. `Shift+Delete`는 휴지통도 거치지 않는다.
- 편집기(Mousepad)로 파일을 덮어쓰는 것.

이 경로들도 exec 정책·승인·삭제 전 스냅샷(AP-2)을 거치지 않는다. 이 부분은 구조상 판단이고 따로 재현하지는 않았다.

그래서 진짜 질문은 하나다: **"데스크톱 템플릿에서 GUI를 보안 경계로 볼 것인가, 아니면 실행 경로로 인정하고 다른 장치로 보완할 것인가."**

### A. 문서화만
- **내용**: README에 "데스크톱 템플릿의 GUI 도구는 컨테이너 안에서 uid 1001로 아무 일이나 하는 것과 같다. exec 허용 목록·승인·삭제 전 스냅샷은 GUI 경로에 적용되지 않는다"를 명시한다. 알려진 한계 항목은 이미 추가했다(`c2f83a3`). 남은 일은 GUI 도구 표의 "허용" 옆에 같은 경고를 다는 정도다.
- **장점**: 비용이 없다. 운영자가 위험을 알고 템플릿을 고른다.
- **단점**: 막는 것이 없다. 다른 방안과 항상 같이 한다.

### B. 이미지 하드닝 (문턱 높이기)
- **내용**:
  - 데스크톱 이미지에서 `xfce4-terminal`을 뺀다.
  - Xfce 단축키(`Ctrl+Alt+T`, `Alt+F2` 실행 창)를 끈다.
  - 패널·독의 터미널 실행기와 "Run Program"을 없앤다.
  - Thunar의 "터미널 열기"와 실행 파일 실행을 막는다.
  - xfconf를 kiosk 모드로 잠가 되살리지 못하게 한다.
- **장점**: 작다. 실측에서 쓴 가장 쉬운 길(단축키 → 터미널)이 사라진다.
- **단점**:
  - **경계가 아니다.** Thunar 삭제, 편집기 덮어쓰기 같은 원래 기능으로 파일 손실은 그대로 가능하다.
  - 빠뜨린 실행 경로(다른 앱의 "열기 방식", autostart 등)가 남을 수 있다.
  - 화면을 인수한 **사람**도 터미널을 잃는다.

### C. GUI 입력 전 자동 스냅샷 (되돌릴 수 있게)
- **내용**: AP-2("파괴적 작업 직전에 스냅샷")를 GUI 경로에도 적용한다. GUI 동작 하나하나가 파괴적인지는 알 수 없으므로, 구간 단위로 뜬다. 언제 뜰지는 세 가지 중 하나를 고른다:
  - C1. 모든 `click`·`type`·`key` 직전: 가장 촘촘하지만, 매번 화면이 약 2.5초 멈춘다(실측). 비현실적이다.
  - C2. **GUI 구간 시작 때 (권장 변형)**: GUI 입력이 N초(예: 60초) 쉬었다가 다시 시작할 때, 또는 마지막 스냅샷이 T분(예: 10분)보다 오래됐을 때 한 번 뜬다.
  - C3. GUI 활동 중 T분마다 한 번.
- **N-3 상한과의 관계**: `AGENTBOX_SNAPSHOT_QUOTA`에 같이 걸린다. 상한에 이르면 GUI 입력도 승인으로 넘긴다. 그러면 사람 없이 디스크를 채우지 못한다.
- **장점**: 에이전트의 자율성은 그대로 두면서 "되돌릴 수 없는 손실"을 막는다. 기존 스냅샷·복원 UI를 그대로 쓴다.
- **단점**:
  - 승인 우회 자체는 남는다. 실행은 되지만 되돌릴 수 있게 되는 것이다.
  - 되돌리면 그 구간 안의 정상 작업도 같이 사라진다.
  - 스냅샷 동안 화면이 약 2.5초 멈춘다(실측, 거의 빈 작업 폴더 기준).
  - 디스크 비용은 작업 폴더 크기에 비례한다(N-3에서 실측).
- **실측 비용**: 데스크톱 스냅샷 1회 2.4~2.8초, 디스크 증가 0.1MB 이하(작업 폴더가 거의 빈 상태).

### G. 변경 감지·기록 (보이게 하기)
- **내용**: 컨테이너 안에서 `/workspace` 변경을 감시해(inotify) GUI 구간이 끝날 때 바뀐 파일·지운 파일 목록을 감사 로그에 남긴다. 지운 파일이 있으면 웹 UI에 표시한다. 감시 프로세스는 root로 돌리고 에이전트·화면 계정은 손대지 못하게 한다.
- **장점**: 사람이 사후에 무엇이 바뀌었는지 안다. C와 붙이면 "무엇을 되돌릴지" 판단하기 쉽다.
- **단점**: 아무것도 막지 않는다. 단독으로는 부족하고 C의 보조다.

### D. GUI 입력마다 승인
- **내용**: 기본 정책에서 `click`·`type`·`key`를 `require_approval`로 바꾼다. 승인 경로가 실행 직전에 스냅샷을 뜨므로 AP-2도 지켜진다.
- **장점**: 보장이 가장 강하다. 정책 파일 한 줄이라 구현이 사실상 없다.
- **단점**: 클릭 하나, 키 하나마다 사람이 승인해야 한다. 데스크톱 템플릿을 쓸 이유가 사라진다. 사람이 직접 조작하는 화면 인수와 다를 바가 없다.

### D2. 시간 제한 GUI 허가
- **내용**: 에이전트가 GUI를 쓰려면 "GUI 조작 N분 허가"를 승인 요청한다. 사람이 승인하면 그 시점에 스냅샷을 뜬다(기존 승인 경로). 이후 N분 동안 GUI 도구는 바로 실행되고, 시간이 지나면 다시 허가를 받아야 한다. 화면 인수의 반대 방향 "임대(lease)"라고 보면 된다.
- **장점**:
  - 사람의 결정이 GUI 경로에도 들어온다.
  - 허가 시점 스냅샷으로 복구도 된다.
  - 허가 중에는 에이전트가 자유롭게 일한다.
  - 승인 화면에 "이 N분 동안 화면으로 무엇이든 할 수 있다"를 분명히 보여 줄 수 있다.
- **단점**:
  - 새 개념(허가·만료·연장)과 UI가 필요하다.
  - 긴 작업은 N분마다 사람이 다시 승인해야 한다.
  - 허가 시간 안의 행동은 여전히 정책 밖이다.

### E. 화면 계정의 `/workspace` 쓰기 분리
- **내용**: 화면 계정(uid 1001)은 `/workspace`를 읽기만 하고, 별도의 화면 작업 폴더(예: `/home/desktop/work`)에서 일한다. 결과를 `/workspace`에 넣으려면 에이전트가 `publish` 같은 도구를 부르게 한다. 그 도구는 정책·승인·스냅샷을 거치는 기존 파일 도구 경로를 쓴다. 구현은 그룹 쓰기 권한을 빼고 setgid를 정리하는 식이다.
- **장점**: GUI로 무엇을 실행하든 **`/workspace`는 정책 밖에서 바뀌지 않는다.** 이 문제에 대한 유일한 진짜 경계다.
- **단점**:
  - "GUI 앱으로 작업 폴더 파일을 바로 고친다"는 지금 사용 흐름이 바뀐다. 반영 단계가 생긴다.
  - 사람이 화면을 인수해 고친 결과도 같은 반영 단계를 거쳐야 한다.
  - 컨테이너 안 실행 자체(네트워크 없음 등은 유지)는 그대로 가능하다.
  - 변경이 크다: 이미지, 권한, 새 도구, 문서, 테스트.

### F. 화면 계정의 실행 제한
- **내용**: AppArmor·seccomp 같은 MAC으로 uid 1001 프로세스가 실행할 수 있는 프로그램을 Xfce와 지정한 앱으로 제한한다. `bash`, `sh`, `python3` 등을 막는다.
- **장점**: 터미널을 열어도 셸이 안 뜬다. 사용성 영향이 작다.
- **단점**:
  - 프로필을 만들고 유지하기 어렵다. Xfce 내부에서 셸을 쓰는 곳이 있다.
  - 런타임마다 지원이 다르다. agentbox가 우선 쓰는 gVisor(runsc)·Kata에서 AppArmor 동작이 다르다.
  - **파일 삭제·덮어쓰기는 여전히 GUI 앱으로 가능하다.** B와 같은 한계다.

### H. 에이전트 GUI 도구 끄기 (설정)
- **내용**: `AGENTBOX_DESKTOP_AGENT_GUI=off` 같은 설정을 둔다. 에이전트는 `screenshot`만 쓰고, 화면 조작은 사람(화면 인수)만 한다.
- **장점**: 작고 확실하다. 위험을 받아들일 수 없는 운영자를 위한 선택지가 된다.
- **단점**: 에이전트가 GUI 앱을 쓰는 기능(TL-2) 자체가 꺼진다. 기본값으로는 맞지 않는다.

## 조합과 권장

방안들은 서로 배타적이지 않다. 현실적인 조합은 셋이다:

| 조합 | 구성 | 성격 |
|---|---|---|
| ① 최소 | A + C2 (+ G) | 자율성 유지 + 복구 가능. 작은 변경으로 AP-2 약속을 GUI에도 지킨다 |
| ② 중간 | A + D2 (+ C2) | 사람의 결정을 GUI에도 넣는다. 새 허가 개념이 필요하다 |
| ③ 강함 | A + E | `/workspace`에 대한 진짜 경계. 사용 흐름이 바뀐다 |

**권장: ① A + C2를 먼저 하고, 필요하면 ②로 간다.**
- 지금 제품의 약속("승인 + 직전 스냅샷")에서, 그대로 지킬 수 있는 쪽(복구)부터 GUI에도 적용하는 가장 작은 변경이다.
- 상한(N-3)과 묶으면 사람 없이 무한히 스냅샷을 뜨지도 못한다.
- B(하드닝)는 경계가 되지 못하고 사람의 터미널만 빼앗으므로 권장에서 뺀다.
- H는 기본값이 아니라 운영자 선택지로 따로 둘 만하다.
- E는 제품 방향("에이전트가 GUI로 무엇을 할 수 있어야 하나")이 정해진 뒤 검토한다.

## 트레이드오프에서 짚은 함정

- **백그라운드 프로세스**: GUI로 띄운 `sleep 3600; rm -rf /workspace/*` 같은 프로세스는 GUI 조작이 없을 때 파일을 바꾼다. C(구간 시작 스냅샷)와 D2(허가 만료)는 이를 막지 못하고, 마지막 스냅샷까지만 되돌릴 수 있다. E만 이 문제가 없다.
- **스냅샷 상한**: C를 단순하게 붙이면 상한에서 클릭마다 승인이 된다. 구현에서는 승인 경로의 스냅샷이 구간을 새로 열게 해서, 상한에서는 "구간마다 한 번 승인"(D2와 비슷)으로 동작한다.
- **복구 정밀도**: 스냅샷은 컨테이너 통째로 되돌린다. 구간 안의 정상 작업과 열려 있던 앱 상태도 사라진다. 간격을 좁히면 화면 멈춤(회당 약 2.5초)이 잦아지고 상한도 빨리 찬다.
- **승인 피로(D2)**: 허가 요청이 잦으면 사람이 기계적으로 승인하게 된다. 승인 대기 상한(300초) 때문에 사람이 자리를 비우면 에이전트가 멈춘다.
- **사람의 화면 인수(E)**: 사람이 GUI로 고친 결과도 반영 단계를 거쳐야 한다.

## 결정과 남은 것

- **선택**: 방안 C, 변형 C2. 사용자가 "가성비"로 골랐다.
  - 기준값: 쉬는 시간 60초(`AGENTBOX_GUI_SNAPSHOT_IDLE`), 최대 간격 600초(`AGENTBOX_GUI_SNAPSHOT_INTERVAL`, 0이면 끔).
  - A(문서화)도 같이 했다. H(에이전트 GUI 끄기)는 넣지 않았다.
- **구현** (`3028b68`):
  - `click`·`type`·`key`만 대상이고 `screenshot`은 빼며, 사람이 조작 중이면 뜨지 않는다.
  - 사람이 화면을 돌려준 뒤 에이전트의 첫 입력에는 스냅샷을 뜬다(사람이 바꾼 상태 보존).
  - 상한에서는 구간 시작만 승인한다.
- **남은 위험**: 승인 우회, 구간 단위 복구의 손실, 백그라운드 프로세스. 더 필요해지면 D2(시간 제한 허가)나 E(쓰기 분리)로 간다.
